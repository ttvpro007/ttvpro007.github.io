Portfolio Architecture

The site is a pure function of the content/ folder. Every page, section, project, image, Unity build, label and color the visitor sees is read from there at build time; code never holds content. The admin GUI and a headless CLI are two front doors onto one module that edits that folder, plus a gated way to ship it.

Once that is clear the rest follows: the Vite plugin exists to turn the folder into data and copy its media, the registries exist so a new kind of media, link or page section is a data change rather than a code change, and the release gate exists because the only thing that can break the live site is content that was never built.

Theming

content/theme.json holds named presets and the active one. At startup applyTheme() writes 11 color tokens, two font stacks and a radius onto :root and injects the Google Fonts link. Stylesheets read only those variables; translucent shades are color-mix(in srgb, var(--color-primary) 30%, transparent) rather than rgba literals, so a shade follows its token. About a hundred hard-coded gold/orange literals were rewritten this way.

The admin's theme editor previews unsaved presets by postMessage into an iframe of the dev site (same-origin only), at phone/tablet/laptop/wide sizes, and reports WCAG contrast for three pairs.

The release gate

Invariants

  • No content in src/. Text, media and colors belong in content/; components receive them from @/data.
  • No theme color literals in components. Use the CSS variables or color-mix() of them. Exceptions are deliberate: canvas effects, the confetti library, brand logos, and the standalone email template in questUtils.js.
  • Media src is relative to the project's media/ folder or an absolute https:// URL; nothing else resolves.
  • The admin API is dev-server only (apply: 'serve') and binds to localhost. It writes files and runs git, so never run npm run admin -- --host on an untrusted network.
  • Deletes from the admin or the CLI go to .trash/ (ignored by git), never straight to removal.
  • layout.json is only ever written in its normalized shape: pages sorted with order = 0…n−1, keys in canonical order, options equal to the type's default dropped. Unknown keys are errors unless they start with _ (notes). The admin's Save, PUT /layout and the CLI store the same bytes for the same layout.
  • Content writes go through admin/server/store.js. A new admin route or CLI command calls a store function rather than touching content/ itself.

Deliberate oddities

Short legacy variable names such as --card-bg, --text and --bg are defined in variables.css as aliases of theme tokens. About twenty components used them after an earlier CSS consolidation removed their definitions, which left cards and the mobile navbar transparent. They are aliases rather than renamed call sites to keep the diff reviewable; migrating them is optional cleanup.

The staging branch is force-pushed. It is a mirror of whatever is under review, not a line of history.

layout.json is not one of the store's SITE_FILES. The generic Site content forms render every file in that list from its JSON shape; the layout has its own reader, writer and validator and its own admin page (Site map), so it is left out on purpose. navigation.json still has a pages array that nothing reads any more; it was kept rather than change that file's format.

The CLI changes directory before it imports anything. plugins/content.js and store.js resolve content/ from the working directory when they load, so cli.js runs process.chdir() (to the repo, or PORTFOLIO_ROOT) and then uses dynamic import(). File arguments are resolved against the directory it was run from. The tests rely on this to run against a temp copy of content/.

Unresolved

  • The HTTP layer, the admin UI and the git side of releasing have no automated tests. The content operations do: 12 CLI tests drive store.js against a temp copy of content/ (create, update guard rails, overview, WebP upload, Unity folder check, media removal, rename, order, theme, site, layout, validate), and 11 more test siteLayout.js directly. The Site map page, and the claim that all four pages kept their DOM when they moved onto layout.json, were checked by hand in a browser. The thin routing in api.js was checked by hand after the refactor, with every write route called through a running dev server. Stage and Go live (commit and push) have never run from the CLI; they are the same functions the GUI uses. Testing them would mean mocking git and child processes, which was judged not worth it for a one-person site.
  • Nested sections are allowed by the format but rendered nowhere. A section node may carry children, and validateLayout already recurses into them for types whose registry entry sets children: true. No type does, and SitePage does not render children, so the first container type (rows, columns) has to add that rendering and its Site map UI; the stored format needs no migration.
  • Media-list editing exists twice. The GUI's MediaPanel.jsx still builds the media list in the browser and uploads files one by one through the API, while the CLI uses store.addMedia / removeMedia for the same work. They follow the same rules (unique slugified names, Unity index.html check, clear the cover and trash the file once it's unused) but are separate code. Moving the GUI onto the store functions would need new routes.
  • Staging relies on one deploy key. ttvpro007/portfolio-staging is deployed by CI with a write deploy key scoped to that repo, stored as STAGING_DEPLOY_KEY. Deploy keys do not expire, so there is no rotation schedule; rotate only if it leaks, using the steps in docs/release.md.
  • Large binaries live in git. The Unity build is about 96 MB of the 113 MB under content/projects. LFS was considered and declined: every CI checkout would download the build, using up the free 1 GB/month LFS bandwidth in about ten deploys, and converting means rewriting history. If the build grows, host it outside the repo (e.g. a GitHub Release asset) instead.
  • Content gaps. Broken videos and wrong links found during the migration were removed rather than replaced. Six of the seven projects have no video, Lumina Adfecto and Planet Runner have no external link, and Unity Physics Simulator and Programming Problems Solution have no images until real screenshots are added.
  • Fonts load from Google at runtime, so the first paint can show fallback fonts.
