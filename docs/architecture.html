Portfolio Architecture

The site is a pure function of the content/ folder. Every project, image, Unity build, label and color the visitor sees is read from there at build time; code never holds content, and the admin GUI is just a local editor for that folder plus a gated way to ship it.

Once that is clear the rest follows: the Vite plugin exists to turn the folder into data and copy its media, the registries exist so a new kind of media or link is a data change rather than a code change, and the release gate exists because the only thing that can break the live site is content that was never built.

Theming

content/theme.json holds named presets and the active one. At startup applyTheme() writes 11 color tokens, two font stacks and a radius onto :root and injects the Google Fonts link. Stylesheets read only those variables; translucent shades are color-mix(in srgb, var(--color-primary) 30%, transparent) rather than rgba literals, so a shade follows its token. About a hundred hard-coded gold/orange literals were rewritten this way.

The admin's theme editor previews unsaved presets by postMessage into an iframe of the dev site (same-origin only), at phone/tablet/laptop/wide sizes, and reports WCAG contrast for three pairs.

The release gate

Invariants

  • No content in src/. Text, media and colors belong in content/; components receive them from @/data.
  • No theme color literals in components. Use the CSS variables or color-mix() of them. Exceptions are deliberate: canvas effects, the confetti library, brand logos, and the standalone email template in questUtils.js.
  • Media src is relative to the project's media/ folder or an absolute https:// URL; nothing else resolves.
  • The admin API is dev-server only (apply: 'serve') and binds to localhost. It writes files and runs git, so never run npm run admin -- --host on an untrusted network.
  • Deletes from the admin go to .trash/ (ignored by git), never straight to removal.

Deliberate oddities

Short legacy variable names such as --card-bg, --text and --bg are defined in variables.css as aliases of theme tokens. About twenty components used them after an earlier CSS consolidation removed their definitions, which left cards and the mobile navbar transparent. They are aliases rather than renamed call sites to keep the diff reviewable; migrating them is optional cleanup.

The staging branch is force-pushed. It is a mirror of whatever is under review, not a line of history.

Unresolved

  • No automated tests. Verification so far is lint, a production build, and a manual browser pass: create/upload/save/delete through the API, WebP conversion (9.1 MB PNG → 2.0 MB), Test gate lock and unlock, theme presets, and overflow checks at 320–2560 px.
  • Staging relies on one deploy key. ttvpro007/portfolio-staging is deployed by CI with a write deploy key scoped to that repo, stored as STAGING_DEPLOY_KEY. Nothing rotates it automatically; the steps are in docs/release.md.
  • The test fingerprint lives in memory. Restarting the dev server, which also happens whenever an admin or plugin file is edited, clears it, and you have to run Test again. It fails safe, but it is surprising.
  • Large binaries live in git. The Unity build is about 96 MB of the 113 MB under content/projects, with no LFS. That is within GitHub Pages' limits, but it makes the repo slower to clone.
  • Content gaps. Broken videos and wrong links found during the migration were removed rather than replaced. Five projects now have no video, Lumina Adfecto and Planet Runner have no external link, and Unity Physics Simulator and Programming Problems Solution have no images until real screenshots are added.
  • Fonts load from Google at runtime, so the first paint can show fallback fonts.
